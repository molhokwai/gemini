# Google Workspace (Sheets · Apps Script · AppSheet)

Global, project-agnostic skill — usable in any session. These three surfaces are covered together deliberately: in practice almost every real gotcha spans two of them (Apps Script writing across two spreadsheets, AppSheet binding to a Sheet by tab name), so splitting them into separate skills risks fragmenting or duplicating the same lesson. Origin: built from a real spreadsheet-consolidation + AppSheet re-link project (2026-09), not a hypothetical — every item below was hit live at least once.

## Google Sheets

- **Address spreadsheets by ID**, via `SpreadsheetApp.openById(id)`, never by name — names can be duplicated or renamed (see Archiving below) and are not stable identifiers.
- **Cross-spreadsheet script pattern**: a disposable *standalone* Apps Script project (not bound to either spreadsheet) operating on both source and destination via `SpreadsheetApp.openById()` is faster to iterate with than a bound script, especially when testing against a safety copy before the real file — no per-spreadsheet re-authorization needed.
- **Tab-name collisions**: a spreadsheet requires unique tab names. `sheet.copyTo(destSS)` auto-renames on collision (e.g. appends `" (1)"`); follow with an explicit `.setName()` if you need the exact original name.
- **Copy-order matters for cross-sheet formulas**: if a copied tab's formula references another tab (e.g. `='Other Tab'!A1`), and that other tab doesn't exist yet in the destination at copy time, the formula resolves to `#REF!` **permanently** — reordering the copy sequence afterward does not fix already-broken formulas, only prevents new breakage. Order tab copies so anything referenced lands before whatever references it. Verify with a dedicated diff script comparing `getFormulas()` and `getValues()` cell-by-cell between source and copy — a clean run with no thrown error is *not* proof the formulas are correct.
- **Disposable-copy cleanup**: `DriveApp.getFilesByName(exactName)` + `.setTrashed(true)` reliably finds and trashes a prior run's same-named safety copy before creating a new one.
- **Archive via rename, not delete**: prefix the old file's name (e.g. `[ARCHIVÉ YYYY-MM-DD — reason] Original Name`) — preserves the file, its ID, and any AppSheet app still bound to it, while making the archival status visible to a human browsing Drive.
- **Always verify on a copy first**: duplicate the target spreadsheet, run and fully verify the migration script against the copy, only then repeat the identical script against the real file. Sheets has no session-wide undo once a script has touched real data.

## Apps Script

- **6-minute execution timeout** is a hard wall for any script iterating row-by-row over a large range. The recurring fix: replace the per-row script logic with `ARRAYFORMULA` + `SUMIF`/`SUMIFS`/`MAXIFS` formulas computed natively by Sheets, rather than a script writing values row-by-row.
- **OAuth "Authorization required"** on a fresh script project genuinely requires a human clicking through a real browser consent popup — there is no tool or API to complete this on the user's behalf. Ask the user to check for the popup and confirm once done.
- **The "Select function to run" dropdown is unreliable to drive by coordinate/keyboard automation** — a short auto-dismiss animation makes clicks and keystrokes miss across tool-call latency, and stray keystrokes can leak into the code editor. **Deterministic fix**: rewrite the whole file via `monaco.editor.getModels()[0].setValue(fullScriptText)` (through a JS-execution tool) so the target function is the *sole* top-level `function` declaration in the file; convert every helper to `var helperName = function(){...}` so it doesn't populate the dropdown as a separate candidate. This makes "Run" deterministic with zero dropdown interaction.
- **Installable `onChange` trigger for API-driven writes**: AppSheet (and anything else writing via the Sheets API) never fires a simple or installable `onEdit` trigger — only an installable **`onChange`** trigger catches those writes: `ScriptApp.newTrigger(fn).forSpreadsheet(ss).onChange().create()`. Since `onChange` reports only *that* something changed, not *which* row, design the handler to scan for and process every row still in a "pending" state rather than assuming "the newest row" — this is also self-healing against a missed or delayed trigger firing.
- **Reusable helpers** worth writing once and keeping around: `normKey_(s)` (accent/case-insensitive string normalization for matching column headers across sheets), `getSheetHeaderIndex_(sh)` (reads row 1 into a `{normalizedHeader: columnIndex}` map so formula-writing code is header-order-independent), `columnToLetter_(col)`.
- **GNU `date` arithmetic gotcha** (bash, not Apps Script, but recurs when scripting around dates): `date -d "<timestamp> + N days"` can silently fail to add days. Use epoch arithmetic instead: `date -d "@$(( BASE_EPOCH + N*86400 ))"`.
- **`sheet.appendRow()` silently lands in the wrong row if the sheet has pre-seeded formula columns.** `appendRow()` relies on `getLastRow()`, which counts *any* non-empty cell — including an `ARRAYFORMULA` (or its spilled results) or a helper column pre-filled down to row 500+ at setup time, even when zero real data rows exist yet. A first real write can land at row 501 instead of row 2. Fix: never use `appendRow()` on a sheet with pre-seeded formula/helper columns; instead compute the true last *data* row by scanning one designated non-formula anchor column only (e.g. a "Type" or "Statut" column that's always plain text), then write with an explicit `getRange(nextRow, 1, 1, width).setValues(...)` using that row.

## AppSheet

- **"Unable to fetch app definition... a plan update is needed" is a misleading generic error** — it fires for at least three unrelated causes, and the text itself is not proof of an actual billing problem. **Don't trust the message; run `Manage > Deploy > Run deployment check` first** — it is the single most diagnostic tool available and will name the *actual* failing check (plan/signin, a real schema mismatch, etc.) instead of the generic banner. Confirmed causes seen in practice, roughly in the order to check them:
  1. **Free-plan + Deployed + Require-signin.** A **Deployed** app that requires user sign-in genuinely is blocked on the Free plan. Fix without paying: **Manage > Deploy > "Return to prototype state"** — a Prototype app with the identical sign-in setting works fine on Free. Check every app on the account at once via **My Account (appsheet.com/account/account) > App Info** — Status and "Minimal plan needed" columns, with an inline reason under any actually-blocked row (a clean row here means this app isn't the Free-plan case, even if its own live link still errors).
  2. **A genuine table schema mismatch** — Deployment Check reports e.g. `Table 'X' has more columns (19) than expected (14)`. This happens when the live spreadsheet's tab gained/lost columns after the app's cached schema was last generated (can predate the current session entirely; not necessarily caused by anything you just did). Fix: open that table's columns, click the **refresh/regenerate icon** next to "View data source" → confirm **"Regenerate structure?"**. Safe — regenerates the app's own column definitions only, never touches spreadsheet data. Re-run Deployment Check to confirm it now passes.
  3. **A stuck live-serving cache**, independent of both of the above and outlasting them: even after the account plan is genuinely correct and Deployment Check reports **"appears ready to deploy!"** with everything passing, the public `/start/<appId>` link can keep showing the stale blocked page for a stretch (cache-busting query params and plain reloads do not clear it). What reliably unstuck it in practice: **actually transition the deploy state** — `Manage > Deploy > Run deployment check > "Move app to deployed state"` (or the reverse, prototype→deployed→prototype) — the state *transition* forces a backend resync that a same-state reload does not trigger. Don't conclude the app is broken from the live link alone while Deployment Check passes; treat Deployment Check as authoritative and the `/start/` link as lagging.
  - Upgrading the account plan (e.g. Free → Starter) does take effect immediately for account-level checks (My Account's plan banner, App Info's per-app warnings) but does **not** by itself clear cause 3's stuck cache — expect to still need the deploy-state toggle afterward.
- **Incidental non-tabular sheet content is not corruption.** If a real data table has something placed to the right of its columns (e.g. a manually-added `Total: 14275` label+value pair sitting in unused columns), AppSheet auto-detects those as extra generic `Column_8`, `Column_9`, etc. This looks alarming (an established 8-column table suddenly showing 11) but is simply an accurate read of the sheet's current content — hide the generic columns (uncheck **Show**) rather than treating it as a schema bug. Similarly, if a table has no natural unique key, AppSheet may auto-add a synthetic `ComputedKey` column (an AppSheet-side formula like `CONCATENATE([Date]...)`, not written into the actual sheet) — this is expected behavior when adding a table via **Add data**, not evidence something went wrong.
- **Version history is a real safety net**, scoped to the app's own definition/schema — completely separate from the underlying spreadsheet's data, which is never at risk from an AppSheet-side mistake. **Manage > Versions > Get version history**: "View" opens a read-only preview of an old version; "Restore (make this version current)" makes a *copy* of it the new current version — non-destructive and itself reversible via the same mechanism. Use liberally as a checkpoint immediately before and after any risky schema change (adding/removing tables, bulk column edits). Caveat: retention is limited to a handful of recent versions by default (older ones roll off) — don't assume a pre-session baseline version will still be there; if it's gone, the fallback is deleting the added tables back to the last known-good *shape* by hand (safe: this only removes AppSheet table bindings, never spreadsheet data).
- **The Google Sheets file picker inside "Add data" only responds to a genuine human click** — triggering it via browser automation produces no visible effect at all (not even an error), while the identical element works instantly for a real click. Hand just that one step to the user; everything *after* file selection (the "select tables" checklist with checkboxes, and the "Add Table 'X'" quick-suggestion chips offered once a source is already connected) is a normal in-page control and fully automatable.
- **A dropdown/combobox that focuses but visibly won't open on click may still accept direct typing.** In AppSheet's Data > Columns Type dropdown specifically (and possibly others built the same way), clicking selects/focuses the control (visible blue border) but never renders an options popup — yet typing the target value directly (e.g. `DateTime`, `LongText`) right after that same click applies it correctly, no popup ever needed. Try this before spending time hunting for the "real" click target.
- **A form field meant for multi-line text must be typed `LongText`, not `Text`, or pasted line breaks silently vanish.** AppSheet auto-detects a plain `Text` type for a new column by default; a `Text` field renders as a single-line input, and pasting (or typing) multi-line content into it collapses every line onto one, with no error or warning — a bug that only shows up once someone pastes real multi-line data, not during casual testing. Fix in **Data > Columns > `<table>` > `<column>` Type**, set to `LongText`. When building a "paste a block of text" form (an Import-style flow), also set the timestamp column to `DateTime` — matching an existing sibling table's column types (rather than trusting auto-detection) is the reliable way to get this right the first time.
- **Deploy status** lives at `#Manage.Deploy.Status` in the app editor URL — states "Your app is a `prototype`" or "...is `deployed`", with a one-click toggle between them (see cause 3 above for why toggling it can matter beyond the plan question itself).
- **An app's data-source binding survives renaming the source spreadsheet** (AppSheet references it by Drive file ID, not name) — so archiving a source spreadsheet via rename (see Sheets section) leaves any AppSheet app still bound to it fully functional; it just keeps writing into the archived file rather than wherever the data was migrated to. This is invisible until someone notices new entries aren't showing up in the new location.
- **One app per spreadsheet is the simpler design, not just a workaround.** Adding a second, separate app bound to a spreadsheet that already has its own app works technically, but a fresh standalone app is more failure-prone to debug (no established-good baseline in its version history) and doesn't gain anything over adding new tables/views directly into the spreadsheet's existing app — prefer extending the existing app when the new tables don't collide by name with anything already there.

## Browser automation quirks, across all three surfaces

- **Screenshot-pixel coordinates can silently mismatch the page's real CSS-pixel layout** (seen with `window.devicePixelRatio` between 0.67 and 0.75, varying by tab in the same browser session) — a click computed from a screenshot lands on the wrong row/element, often one row off, with no error. Symptom: repeated clicks at a coordinate that "looks right" in the screenshot keep re-selecting the same wrong element. Fix: stop guessing coordinates from screenshots — use the browser automation tool's accessibility-tree element search to get an element reference and click via that `ref`, which resolves correctly regardless of the scale mismatch. If a tool only takes raw coordinates, compute the actual click point from the real DOM (`element.getBoundingClientRect()` via a JS-execution tool) rather than from the screenshot image.
- **Clicks silently stop registering entirely** after extended interaction on both the AppSheet editor and Google Sheets (a click has no visible effect at all, not even wrong-target selection) — the fix each time was a full page reload (navigate to the same URL), never just retrying the click.
- **The "You're currently signed in as..." Google account-switcher popup** appears unpredictably on Apps Script and other Google surfaces and reliably blocks automated clicks on itself (though it doesn't block the rest of the page) — ask the user to click its **OK** button; don't keep retrying the automated click.
- **A stray keystroke sequence can pop open Google Sheets' "Import file" dialog** (e.g. certain focus/`ctrl+a`-then-type sequences aimed at what was meant to be the Name Box) — recognizable by the "My Drive / Shared with me / Recent / Upload" file-picker UI appearing out of nowhere. Press `Escape` (a plain click on its own close button may not register) and re ‐verify the intended selection/edit didn't happen before retrying.
